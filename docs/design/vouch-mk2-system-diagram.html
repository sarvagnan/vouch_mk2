Vouch Mk2 system diagram

Vouch Mk2 is a repository-local policy engine and evidence ledger. It does not deploy software itself; it becomes a hard release gate when a project's CI/CD workflow makes Vouch's verdict a prerequisite for merge and deployment.

One policy authority The Policy IR owns state machines, transition gates, obligations, and assurance tiers.
One recorded history A content-addressed event log is authoritative; state.json is its derived cache.
One enforcement seam Project jobs → Vouch check/formal → deployment, with forge governance around the whole chain.

01

System internals

Policy decisions are pure; filesystem and process effects stay in thin adapters and the store boundary.

The central guarantee: gate evaluation and state transition are the same code path. A transition cannot be accepted first and checked later by an unrelated handler.
02

The only mutation path

Writers serialize the complete read–decide–apply–commit operation and publish immutable objects before the snapshot that references them.

1Acquire writer lockOne exclusive lock covers the whole logical mutation.
2Read one snapshotStrict decode; unknown fields and unsafe coercions are refused.
3Decide and applyReturn violations, or fold the accepted typed events.
4Write immutable objectsSupporting artifacts and event records become durable first.
5CAS snapshot swapAtomically replace state.json at the expected revision.
Refused decision: structured violations are returned and Vouch state remains unchanged.
Crash before snapshot swap: at worst, inert unreferenced objects remain for later cleanup.
Crash after snapshot swap: the visible snapshot already names durable objects and event records.
03

How a project starts using Vouch

Initialization installs a closed set of repository files, but the adopter deliberately owns the final CI and forge wiring.

  1. Obtain the released lock

    Use the offline vouch.lock artifact built for Python 3.14 or newer.

  2. Initialize the repository

    Choose an assurance tier and name the project test jobs that must gate Vouch.

  3. Add the printed caller job

    Copy it into the existing workflow that owns those tests. The same-workflow needs: edge is the real project-test gate.

  4. Protect the enforcement seam

    Configure required checks, branch protection or a ruleset, and the chosen bot-commit policy at the forge.

  5. Start governing units

    Specify work, freeze its acceptance pack, record evidence, publish the unit, and roster it into releases.

python3 vouch.lock init \
  --project . \
  --lock vouch.lock \
  --tier standard \
  --test-job unit-tests \
  --test-job lint

04

Unit lifecycle and release gates

Vouch gates both completion of individual work units and progression of the operational release record.

GateMechanically enforced conditions
G1 · FreezePack version recorded; declared dependencies exist; no blocking deviation.
G2 · PublishPack frozen; dependencies are published or release-bound; no blockers; tier evidence satisfied. Standard/high require current-pack RED → GREEN with no later RED. High additionally requires an anchor beyond genesis and a formal certificate.
CI readinessEvent-log replay, object and pack integrity, bound pack files unchanged, evidence chains and anchors, projection freshness, standing invariants, strict CI policy, followed by exhaustive formal.
G3 · Prepare releaseNon-empty dependency-closed roster; every member is published or release-bound, has a pack, and has no blocking deviation. Included published units become release-bound.
G4 · Start deployLedger-native launch criteria are present before the release leaves prepared.
G5 · CompleteEvery exact roster binding still resolves; every member remains release-bound with a pack and no blocker; launch criteria are still recorded.

06

Important current boundaries

These are material limits to account for when claiming that every deployment is “gated by Vouch.”

Bundle binding is not yet mandatory

bind-bundle is recommended and verified when present, but neither start-deploy nor complete currently requires a bundle inventory.

Deployment wiring belongs to the adopter

The generated workflow validates and anchors evidence. It does not call prepare-release, operate a deployment platform, or automatically make a deployment job depend on Vouch.

Forge enforcement is external

Required checks, branch protection, workflow integrity, ruleset bypasses, GitHub App credentials, and fork permissions are organizational controls.

Identity is recorded, not authenticated

Actor, run ID, and go/no-go authority values are caller-supplied claims. Vouch checks their structure and history, not the real identity behind them.

Evidence has a narrow claim

Vouch proves the exit status of the process it spawned. It does not prove test adequacy, test-runner honesty, or causal chronology relative to implementation.

Trust-root rewrite remains out of scope

An actor able to coordinate changes to vouch.lock, the workflow, and forge rules can defeat any repository-local mechanism.

Practical release rule: make the real deployment job depend on adopter tests plus a Vouch gate that runs check --ci, formal, and the appropriate release lifecycle commands. Protect that dependency at the forge.
